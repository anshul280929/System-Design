🧱 D — Dependency Inversion Principle (DIP)
📌 Definition

👉 High-level modules should not depend on low-level modules. Both should depend on abstractions.
👉 Abstractions should not depend on details. Details should depend on abstractions.

🧠 Think Like a 10-Year-Old

Imagine you have a switch and a bulb 💡

Switch should work with any bulb
Not just one specific bulb brand

👉 So:

Switch connects to a standard socket (abstraction)
Bulb fits into that socket

✔ You can change bulb anytime
❌ No need to change switch

👉 That is DIP

❌ Bad Example (Violating DIP)
class Keyboard {
    void type() {
        System.out.println("Typing...");
    }
}

class Computer {
    Keyboard keyboard = new Keyboard();  // tightly coupled

    void start() {
        keyboard.type();
    }
}
🚨 Problem:
Computer (high-level) depends directly on Keyboard (low-level)
If keyboard changes → must modify computer

❌ Tight coupling
❌ Not flexible

✅ Good Example (Following DIP)
Step 1: Create abstraction
interface InputDevice {
    void type();
}
Step 2: Low-level modules depend on abstraction
class Keyboard implements InputDevice {
    public void type() {
        System.out.println("Typing with keyboard");
    }
}

class TouchScreen implements InputDevice {
    public void type() {
        System.out.println("Typing with touchscreen");
    }
}
Step 3: High-level module uses abstraction
class Computer {
    InputDevice inputDevice;

    Computer(InputDevice inputDevice) {
        this.inputDevice = inputDevice;
    }

    void start() {
        inputDevice.type();
    }
}
Step 4: Usage
public class Main {
    public static void main(String[] args) {
        Computer c1 = new Computer(new Keyboard());
        c1.start();

        Computer c2 = new Computer(new TouchScreen());
        c2.start();
    }
}
✅ Now:
Computer depends on InputDevice (interface)
You can change device anytime

✔ Flexible
✔ Scalable
✔ Loosely coupled

🌍 Real-World Application
Example: Payment System 💳

Instead of:

❌ OrderService directly using UPI or Card

✅ Use abstraction:

Payment (interface)
UPI, Card, Wallet (implementations)

👉 Easily switch payment method without changing core logic

🧠 When Should You Use DIP?

Use DIP when:

✔ Building scalable systems
✔ Working with multiple implementations
✔ Using Spring Boot / Dependency Injection
✔ Want loose coupling

⚙️ Benefits
✅ Loose coupling
✅ Easy testing (mocking)
✅ High flexibility
✅ Better architecture
✅ Easy to extend
⚠️ Common Mistake

👉 Direct object creation inside class

Bad:

Keyboard k = new Keyboard();

👉 Instead use:

Constructor Injection
Dependency Injection
🎯 Interview One-Liner

👉 “High-level modules should depend on abstractions, not on concrete implementations.”
